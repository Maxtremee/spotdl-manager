# Coding Conventions

**Analysis Date:** 2026-04-23

## Tooling

**Formatter & Linter:** Biome 2.2.4 (single tool for both)
- Config: `biome.jsonc`
- Scripts:
  - `pnpm format` → `biome format`
  - `pnpm lint` → `biome lint`
  - `pnpm check` → `biome check` (full pass used before commits)
- Enforced rules (from `biome.jsonc`):
  - `formatter.indentStyle: "tab"` (all indentation is tabs)
  - `javascript.formatter.quoteStyle: "double"` (double quotes only)
  - `javascript.formatter.trailingCommas: "all"` (trailing commas in multiline lists)
  - Lint rule `style.useBlockStatements: "error"` (always use `{}` blocks, e.g. in `if`)
- Scope: `./src/**/*`, plus `package.json`, `biome.jsonc`, `panda.config.ts`, `postcss.config.cjs`, `tsconfig.json`, `vite.config.ts`
- Explicitly excluded: `src/routeTree.gen.ts` (generated by TanStack Router)

**TypeScript:** 5.9.3 with `strict: true`
- Config: `tsconfig.json`
- `noUnusedLocals: true`, `noUnusedParameters: true`, `noFallthroughCasesInSwitch: true`
- `verbatimModuleSyntax: true` — use explicit `import type { ... }` for type-only imports
- `moduleResolution: "bundler"`, `allowImportingTsExtensions: true`
- JSX configured for Solid: `jsx: "preserve"`, `jsxImportSource: "solid-js"`
- Typecheck via `pnpm typecheck` (`tsc --noEmit`)

## Path Aliases

**Alias:** `~/*` → `./src/*` (configured in `tsconfig.json` and via `vite-tsconfig-paths` in `vite.config.ts`)

```typescript
import { Button } from "~/components/ui/button";
import { PlaylistSchema } from "~/modules/client/playlist/schema/playlist";
import { getDb, schema } from "~/modules/server/db";
```

**Additional aliases (Vite resolves them via PandaCSS codegen):**
- `styled-system/css`, `styled-system/jsx`, `styled-system/patterns`, `styled-system/recipes` — generated PandaCSS utilities (never edit)

**Relative imports** are used inside a single feature folder (e.g., `./PlaylistScheduler`, `../db/schema`). Cross-module imports use `~/`.

## Naming Patterns

**Files:**
- Client UI components: `kebab-case.tsx` — e.g., `src/modules/client/playlist/components/playlist-config-card.tsx`, `src/components/ui/close-button.tsx`
- Client services/schemas: `kebab-case.ts` — e.g., `src/modules/client/playlist/schema/create-playlist-form.ts`, `src/modules/client/playlist/service/playlist-actions.ts`
- Server classes: `PascalCase.ts` when the file exports a class that matches — e.g., `src/modules/server/scheduler/PlaylistScheduler.ts`, `src/modules/server/spotdl/SpotdlInvocator.ts`, `src/modules/server/events/EventBus.ts`
- Server functions/repositories: `lowercase.ts` — e.g., `src/modules/server/playlist/functions.ts`, `src/modules/server/playlist/repository.ts`
- Tests: `<subject>.test.ts` co-located with source — e.g., `src/modules/server/scheduler/PlaylistScheduler.test.ts`
- Routes: file-based via TanStack Router in `src/routes/` (route segments use `.` dot notation for hierarchy, `$param` for dynamic segments, `_` trailing for "with children" flag). Do not hand-edit `src/routeTree.gen.ts`.

**Functions:**
- `camelCase` for all exported and local functions: `formatDuration`, `buildQueryParams`, `createMockPlaylist`
- Server functions end with `ServerFn`: `listPlaylistsServerFn`, `createPlaylistServerFn`, `triggerPlaylistSyncServerFn`

**Variables:**
- `camelCase` for locals/props
- `UPPER_SNAKE_CASE` for module-level constants: `SAMPLE_PLAYLISTS`, `STUB_PLAYLISTS`

**Types & Schemas:**
- `PascalCase` for types and Zod schema identifiers: `Playlist`, `PaginationState`, `PlaylistSchema`, `PlaylistSourceSchema`
- Zod schemas use the `...Schema` suffix
- Event types use dotted kebab string literals: `"playlist.sync.started"`, `"playlist.sync.completed"`, `"scheduler.reload"`

**Components:**
- Solid components exported as `PascalCase` functions: `export function PlaylistConfigCard(props: ...) { ... }`
- Props interface named `<Component>Props`: `PlaylistConfigCardProps`, `ButtonProps`

## Module Boundaries

Strict client/server split under `src/modules/`:

```
src/modules/
├── client/          # Client-safe code bundled into SPA (no Node APIs)
│   └── [feature]/
│       ├── schema/      # Zod validators + inferred types
│       ├── service/     # Pure business logic, formatters, no side effects
│       ├── components/  # Solid components
│       └── utils/       # Helpers (mapper, etc.)
│
└── server/          # Server-only (Nitro/Node APIs allowed)
    ├── db/              # Drizzle schema, init, seed
    └── [feature]/
        ├── repository.ts  # Drizzle queries (data access)
        └── functions.ts   # createServerFn handlers
```

**Rule:** Never import from `~/modules/server/*` inside anything under `~/modules/client/*` or `src/components/`. Server files may freely import client schemas (they are pure Zod/types), e.g. `src/modules/server/playlist/functions.ts` imports `PlaylistSchema` from `~/modules/client/playlist/schema/playlist`.

## Solid.js Conventions

- **Functional components only** — no class components.
- Accept `props` as a single argument and access reactively (`props.foo`). Never destructure props at the top level.
- Use Solid primitives `Show`, `For`, `Suspense` instead of conditional JSX or `.map()`.
- Event handlers and derived values use `Accessor<T>` types when passed across components:
  ```typescript
  interface Props {
    isUpdating: Accessor<boolean>;
    onStatusChange: (status: string) => void;
  }
  ```
- Prefer `splitProps` / `mergeProps` from `solid-js` when wrapping library primitives (see `src/components/ui/button.tsx`).

## UI Components

61 pre-built wrappers live in `src/components/ui/` (e.g., `button.tsx`, `card.tsx`, `dialog.tsx`, `field.tsx`). They wrap Ark UI primitives via `@ark-ui/solid/factory` + PandaCSS recipes.

**Rules:**
- Always import from `~/components/ui/*`, not directly from `@ark-ui/solid/*` in feature code.
- Many components expose a namespace export — import as namespace:
  ```typescript
  import * as Card from "~/components/ui/card";
  import * as Field from "~/components/ui/field";
  import * as Select from "~/components/ui/select";

  <Card.Root>
    <Card.Header>
      <Card.Title>...</Card.Title>
    </Card.Header>
    <Card.Body>...</Card.Body>
  </Card.Root>
  ```
- Single-export components use a default named import: `Button`, `Text`.

## Styling (PandaCSS)

- Theme tokens live in `src/theme/tokens/`, recipes in `src/theme/recipes/`, color palettes in `src/theme/colors/`.
- Config: `panda.config.ts`. Run `pnpm prepare` (alias for `panda codegen`) after any theme change.
- Generated utilities in `styled-system/` (do not edit, do not commit edits). Import from the three main entrypoints:

```typescript
import { css } from "styled-system/css";
import { hstack, vstack, stack } from "styled-system/patterns";
import { button, card } from "styled-system/recipes";
```

**Usage patterns:**

```tsx
// Inline atomic styles via css()
<div class={css({ mb: "6", p: "4", color: "fg.default" })}>

// Layout primitives via patterns
<div class={hstack({ justify: "space-between", w: "full" })}>
<div class={vstack({ gap: "4", alignItems: "stretch" })}>

// Responsive values
class={css({ display: { base: "block", md: "grid" } })}

// Token references inside raw CSS strings
class={css({ borderTop: "1px solid token(colors.border.default)" })}
```

- Use `class={...}` (Solid attribute), never `className`.
- Avoid raw CSS values — always use theme tokens (`fg.default`, `gray.surface.bg`, `colors.border.default`, spacing scale `"4"`, `"6"`, etc.).
- Colors use Radix-style palettes; the root applies `colorPalette: "grass"` (see `src/routes/__root.tsx`).

## Zod / Validation

- All external inputs validated with Zod 4.3.5. Schemas live under `src/modules/*/schema/`.
- Infer TS types from schemas rather than hand-writing them:
  ```typescript
  export const PlaylistSchema = z.object({ ... });
  export type Playlist = z.infer<typeof PlaylistSchema>;
  ```
- Expose both strict and safe parsers when consumed by UI:
  ```typescript
  export function parsePlaylist(data: unknown): Playlist {
    return PlaylistSchema.parse(data);
  }
  export function tryParsePlaylist(data: unknown) {
    return PlaylistSchema.safeParse(data);
  }
  ```
- Prefer `z.discriminatedUnion("type", [...])` for tagged variants (see `PlaylistSourceSchema` and `PlaylistScheduleSchema` in `src/modules/client/playlist/schema/playlist.ts`).
- Use `.describe(...)` liberally — descriptions are the single source of documentation for field semantics.
- Use `.default(...)` to encode safe defaults; `.min`/`.max`/`.int`/`.url` for constraints; custom `.refine(...)` for cross-field/regex validation (e.g., cron expression regex).
- Route search params: validate with `zodValidator` + `fallback` from `@tanstack/zod-adapter`:
  ```typescript
  const playlistSearchSchema = z.object({
    page: fallback(z.int().positive(), 1).default(1),
    search: fallback(z.string(), "").default(""),
  });
  ```
- Environment: validated once via `@t3-oss/env-core` + Zod in `src/env.ts`. Client vars must be prefixed `VITE_`.

## Server Functions

Pattern used everywhere in `src/modules/server/*/functions.ts`:

```typescript
import { createServerFn } from "@tanstack/solid-start";
import { z } from "zod";

const createPlaylistInputSchema = PlaylistSchema.omit({ id: true, createdAt: true, updatedAt: true });

export const createPlaylistServerFn = createServerFn({ method: "POST" })
  .inputValidator(createPlaylistInputSchema)
  .handler(async ({ data }) => {
    try {
      const result = await PlaylistRepository.createPlaylist(data);
      return { success: true, data: result };
    } catch (error) {
      console.error("Failed to create playlist:", error);
      return {
        success: false,
        error: error instanceof Error ? error.message : "Failed to create playlist",
      };
    }
  });
```

**Conventions:**
- One exported server function per operation, named `<verb><Noun>ServerFn`.
- Method is `"GET"` for reads, `"POST"` for any mutation (incl. delete).
- Always declare input schema above the function (don't inline it).
- Reuse client schemas where possible (`PlaylistSchema.omit({...})`) to keep a single source of truth.
- Handler never touches the DB directly — it calls a repository. Repositories live in the same feature folder.
- Return a `{ success, data?, error? }` shape for mutations; return the raw data for reads (throwing if not found is OK for loaders).

## Service Layer

Client-side services hold pure formatting/state logic (no side effects, no DOM, no network). They are exported as an object literal with methods:

```typescript
// src/modules/client/playlist/service/playlist.ts
export const PlaylistService = {
  buildQueryParams(filter, pagination) { ... },
  parseQueryParams(queryString) { ... },
  getDefaultPagination(): PaginationState { ... },
  formatStatus(status): string { ... },
  getStatusVariant(status): "default" | "success" | "warning" | "error" { ... },
  truncateText(text, maxLength = 50): string { ... },
  formatDate(date: Date): string { ... },
};
```

**Rules:**
- Components never embed formatting logic inline — call `PlaylistService.formatX(...)`.
- Services never call server functions directly; components call server functions and pass results to services for formatting.
- Standalone helpers (one-off pure functions) live as named exports in `service/*.ts` instead of on the service object (see `src/modules/client/invocation/service/duration.ts` exporting `formatDuration`, `formatDurationFromDates`).

## Repository Layer

Server repositories encapsulate all Drizzle queries and row ↔ domain conversions.

**Two styles coexist:**

1. **Object-literal repository** (stateless helpers, e.g., `PlaylistRepository` in `src/modules/server/playlist/repository.ts`):
   ```typescript
   export const PlaylistRepository = {
     async listPlaylists(params) { const db = getDb(); ... },
     async getPlaylistById(id) { ... },
     async createPlaylist(playlist) { ... },
   };
   ```

2. **Class repository** (when owning state / dependencies, e.g., `InvocationRepository` in `src/modules/server/invocation/repository.ts`):
   ```typescript
   export class InvocationRepository {
     private readonly db: TDatabase;
     constructor() { this.db = getDb(); }
     async create(data: NewInvocationRow) { ... }
   }
   ```

**Rules:**
- Always call `getDb()` / `schema` via `~/modules/server/db`.
- Build dynamic WHERE clauses with `const conditions: SQL[] = []` pattern, then `conditions.length > 0 ? and(...conditions) : undefined`.
- Clamp pagination: `Math.max(1, params.page || 1)` and `Math.min(100, Math.max(1, params.limit || 10))`.
- Convert between DB rows and domain types via dedicated mappers under `~/modules/client/*/utils/mapper.ts`.

## Error Handling

- **Server functions (mutations):** wrap handler body in `try/catch`, return `{ success: false, error: message }` instead of throwing. Message is derived via `error instanceof Error ? error.message : "Default message"`.
- **Server functions (reads):** throwing is acceptable for "not found" (it propagates to the route loader).
- **Unknown error narrowing:** always check `error instanceof Error` before accessing `.message`.
- **Node filesystem errors:** narrow with the `NodeJS.ErrnoException` cast when checking `.code === "ENOENT"`:
  ```typescript
  if ((error as NodeJS.ErrnoException).code === "ENOENT") { ... }
  ```
- Event handlers catch their own errors internally (see `EventBus.emit` — one handler throwing must not break others).

## Logging

Pino-based singleton in `src/logger.ts`. **Server-only.**

```typescript
import { Logger } from "~/logger";

// Module-scoped logger created at import time
const logger = Logger.get("SpotdlSettings");

logger.info({ useCookies: data.useCookies }, "Spotdl settings updated");
logger.warn({ error, cookiesFile }, "Failed to delete cookies file from filesystem");
logger.error({ error }, "Failed to update spotdl settings");
```

**Rules:**
- Always use a scoped logger — `Logger.get("ModuleName")` — never the bare singleton.
- Pass structured data as the first argument (object), human-readable message as the second.
- Classes that need a logger take an optional `AppLogger` in the constructor, defaulting to `Logger.get("ClassName")` (see `PlaylistScheduler`, `DiscordWebhookService`, `EventHandlerRegistry`). This enables test injection.
- Log level controlled by `LOG_LEVEL` env var; dev defaults to `debug` with pretty output, prod to `info` with JSON.
- Client code uses plain `console.error` only where server-function results need to be surfaced locally; do not import `~/logger` into `src/modules/client/*`.

## Import Organization

Biome handles import ordering automatically via `pnpm format`. Observed order in the codebase:

1. Node built-ins with `node:` prefix (`node:crypto`, `node:fs`, `node:path`)
2. Third-party packages (`@tanstack/...`, `drizzle-orm`, `solid-js`, `zod`, `@ark-ui/...`)
3. Generated `styled-system/*` imports
4. Aliased imports (`~/components/...`, `~/modules/...`, `~/logger`)
5. Relative imports (`./`, `../`)

Use `import type { ... }` for type-only imports (`verbatimModuleSyntax` requires it).

## Comments & Docs

- JSDoc `/** ... */` blocks on exported functions, server functions, repositories, classes, and schema exports. Keep them short — one sentence describing purpose.
- Inline `//` comments only when intent isn't obvious from the code.
- Zod `.describe(...)` replaces field-level JSDoc on schemas.
